Why we build design systems before writing a single page

Design March 18, 2026 CraftedPixel

The pressure is always the same: stakeholders want to see screens. We get it—pixels feel like progress. But when you skip the system layer, you are not buying speed; you are renting chaos.

Over the last few years we have watched the same pattern repeat: teams rush into high-fidelity pages, fork components for one-off tweaks, and six weeks later every screen is a slightly different button radius. Engineering slows down because nothing composes. Marketing cannot self-serve because there is no documented pattern for promos or forms.

Design systems are not a Figma vanity project. They are the contract between brand, product, and engineering.

What we do in week one instead

We start with primitives: type scale, spacing rhythm, color roles (not just hex codes), and elevation. Then we define the smallest set of components that cover 80% of UI—buttons, inputs, cards, navigation shells—before we design a single marketing layout.

That order matters because marketing pages are just compositions of the same atoms your product uses. If the system is honest, your homepage and your logged-in dashboard feel related without being clones.

How we keep it lightweight

We are not trying to ship Material Design on day one. We document decisions as we go: usage notes, do/don’t examples, and token names that match what developers actually implement. The goal is a living kit your team can extend—not a museum catalog nobody opens.

  • Tokens first, then components, then templates.
  • One owner for merges—whether that is design or eng—so drift gets caught early.
  • Storybook or equivalent for anything that ships to production.

When we would not insist on this

If you are validating a risky idea with a disposable landing page and no product surface yet, a full system might be overkill. We still capture decisions in a lightweight style tile so the next phase does not start from zero.

If you are mid-flight with an existing codebase, we meet you where you are: audit what is shipped, align naming, and grow the system outward instead of freezing the roadmap for a “big bang” redesign.

Handoff that engineering actually trusts

Pretty Figma files are not enough. We pair components with naming that matches the repo, default states, empty states, and error states—not only the happy path. When eng opens a ticket, they should see the same vocabulary in design and in code.

That usually means a short mapping doc: token name → CSS variable or theme key; component name → React (or Vue) file; any third-party primitives you rely on. The first sprint after handoff should feel boring, not like archaeology.

What we ship by day ten

By the end of the second week you should have: a type and color scale you can defend in a stakeholder review, eight to twelve core components in Figma with variants, and a one-page “how to extend this” note. Not a hundred icons—just enough surface to build a real homepage section and one product screen without inventing new patterns.

If you are already feeling pressure to skip straight to pages, slow down long enough to lock those primitives. The pages will catch up—and they will not fight each other when marketing runs a promo and product ships a settings refresh in the same month.
